# 生产站点定时巡检设计

## 目标

为当前生产静态站点增加独立的可用性巡检。巡检由 GitHub Actions 每 30 分钟运行一次，也可以在 Actions 页面手动触发。它只读取公网资源并报告结果，不登录服务器、不修改发布目录、不重启 Nginx，也不执行自动回退。

本次只实现自动化事项 5“定时线上巡检”。失败通知和 Lighthouse 性能检查将在后续独立设计中实现。

## 已确认的规则

- 巡检目标是当前生产站点，地址通过仓库级 GitHub Actions Variable `MONITOR_URL` 提供。
- 每 30 分钟自动巡检一次，并支持 `workflow_dispatch` 手动运行。
- 单次网络波动不能立即判定站点故障；请求使用有限超时和最多 3 次重试。
- 巡检必须验证首页响应、HTML 类型、Vue 挂载点，以及首页直接引用的 JavaScript 和 CSS。
- 任一必要检查失败时，工作流以失败状态结束并给出可定位的错误信息。
- 巡检失败不自动回退版本、不重启服务、不修改服务器状态。
- 定时巡检与 Tag 生产部署使用不同工作流和并发组，互不修改对方的执行逻辑。

## 方案选择

考虑过三种方案：

1. 将全部 `curl` 命令直接写在 GitHub Actions YAML 中。文件少，但检查逻辑难以本地测试，YAML 也会快速变得难以维护。
2. 使用独立 Shell 巡检脚本，由 GitHub Actions 负责调度。脚本可以在本地和测试夹具中运行，工作流只负责传入配置并呈现结果。
3. 使用第三方可用性监控服务。外部探测通常更稳定，但需要额外账号、服务配置和新的信任边界。

采用方案 2。它延续仓库现有“Shell 承担运维逻辑、工作流承担编排、测试验证契约”的模式，同时不增加第三方服务依赖。

## 组件边界

### 巡检脚本

新增 `scripts/monitor/check-site.sh`。脚本接收且只接收一个完整的 `http` 或 `https` URL，负责：

1. 校验 URL 非空、格式可接受且不包含空白或换行。
2. 使用 `curl` 请求首页，限制连接时间、单次请求总时间和整体重试时间。
3. 要求最终响应为 HTTP 成功状态。
4. 从响应头中读取 `Content-Type`，忽略大小写并允许参数，要求媒体类型为 `text/html`。
5. 检查 HTML 中存在 Vue 应用挂载点 `id="app"`。
6. 使用结构化的 HTML 解析辅助程序读取首页直接引用的模块脚本和样式表 URL，而不是用正则拼接 HTML。
7. 根据最终响应 URL 解析相对地址，只允许继续检查同源的 `http` 或 `https` 资源。
8. 对每个直接引用的 JavaScript 和 CSS 资源执行有界请求，并要求 HTTP 成功。
9. 输出简洁的成功摘要；失败信息指出失败阶段和目标 URL，但不输出响应正文。

脚本不读取 GitHub Secrets，也不包含服务器 SSH 逻辑。临时响应文件使用安全临时目录并通过 trap 清理。

### HTML 资源解析器

新增小型 Python 3 辅助程序 `scripts/monitor/extract-assets.py`，负责结构化验证 Vue 挂载点，并将 HTML 和最终响应 URL 转换为经过校验的同源 JavaScript/CSS URL 列表。它使用 Python 标准库的 `html.parser.HTMLParser` 和 `urllib.parse` 解析 HTML、相对路径与同源关系，不引入第三方依赖。解析器不发起网络请求，也不决定重试策略。

解析器只选择：

- `id` 准确等于 `app` 的 Vue 挂载元素；
- 带 `src` 的模块脚本；
- `rel` 包含 `stylesheet` 且带 `href` 的链接。

资源列表去重。没有找到至少一个模块脚本和至少一个样式表时视为失败，因为当前 Vite 生产首页必须同时引用这两类构建产物。

### GitHub Actions 工作流

新增 `.github/workflows/monitor.yml`，工作流使用：

- `schedule`：每 30 分钟运行；
- `workflow_dispatch`：允许人工立即运行；
- `permissions: contents: read`：只读仓库；
- 独立的监控并发组，允许正在运行的巡检完成，并避免重复巡检占用执行器；
- 明确的 job 和 step 超时；
- 固定到完整提交 SHA 的官方 checkout Action；
- 仓库级 Variable `MONITOR_URL`，不引用 `production` Environment，因此巡检不会生成生产部署记录，也接触不到部署 Secrets。

工作流先校验 `MONITOR_URL`，再检查 Shell 和 Python 脚本语法，最后执行真实公网巡检。它不安装项目依赖，也不在每次定时任务中运行完整测试，避免把 npm 服务异常误判为生产站点故障。真实巡检失败会使工作流变红，为下一阶段的失败通知提供稳定信号。

## 数据流

1. GitHub 定时器或用户手动操作触发工作流。
2. 工作流从仓库级 Variable 读取 `MONITOR_URL`。
3. 工作流检出默认分支最新提交并检查巡检脚本语法。
4. 工作流调用巡检脚本并传入 `MONITOR_URL`。
5. 脚本请求首页，将 HTML、最终响应 URL 和响应类型保存到临时目录。
6. HTML 解析器输出同源的 JavaScript/CSS URL。
7. 脚本逐个请求这些资源。
8. 全部成功时工作流为绿色；任一检查失败时为红色。

## 超时、重试与并发

首页和静态资源请求均设置连接超时与单次请求总超时，并只对短暂网络错误重试。重试次数最多为 3 次，整体请求时间有硬上限，避免 GitHub Runner 因半开连接长期占用。

监控工作流使用独立固定并发组。若上一次巡检仍在运行，新触发的巡检不应取消正在执行的请求；工作流的总超时必须大于所有步骤预算之和，并保留清理余量。

GitHub 定时任务可能延迟，30 分钟表示期望频率而不是严格实时 SLA。本项目现阶段接受这一限制；需要分钟级告警或更强可用性保证时，再评估外部监控平台。

## 错误处理与日志

错误按以下类别输出：

- 配置错误：`MONITOR_URL` 缺失或格式无效；
- 首页不可用：连接、TLS、超时或 HTTP 状态失败；
- 内容错误：响应不是 HTML 或缺少 Vue 挂载点；
- 构建资源错误：首页没有可验证的 JS/CSS，或解析到跨源/非法 URL；
- 静态资源不可用：具体 JS/CSS 请求失败。

日志可以显示公开 URL、HTTP 状态和检查阶段，但不输出完整 HTML、响应头中的敏感值或任何 GitHub Secret。脚本始终清理临时文件。

## 测试策略

### 脚本集成测试

使用本机临时 HTTP 服务构造以下场景：

- 正常 HTML、模块脚本和样式表全部可用；
- 首页返回非成功状态；
- 首页 `Content-Type` 不是 HTML；
- HTML 缺少 `id="app"`；
- HTML 没有模块脚本或样式表；
- 某个直接引用资源返回失败；
- 相对 URL 以重定向后的最终页面 URL 为基准正确解析并去重；
- 跨源或非 HTTP(S) 资源被拒绝；
- URL 包含空白或换行时在网络请求前失败；
- 失败和信号中断后临时目录被清理。

测试不访问真实公网，结果必须可重复。

### 工作流契约测试

使用现有 YAML 解析依赖验证：

- 触发器仅包含 30 分钟定时和手动运行；
- 权限为只读；
- 不声明 `production` Environment，不读取部署 Secrets；
- 使用仓库级 `MONITOR_URL`；
- 官方 checkout Action 固定完整提交 SHA；
- 所有步骤和 job 都有合理超时；
- Shell 和 Python 语法检查在真实巡检之前运行；
- 工作流调用仓库内的巡检脚本。

### 回归验证

实现完成后运行巡检脚本集成测试、工作流契约测试，以及现有 lint、类型检查、Vitest、部署脚本测试和生产构建，确认新巡检没有改变 Tag 部署行为。定时工作流本身不重复运行这些完整测试。

## 配置与启用

代码合并到 `main` 后，仓库管理员需要在：

`Settings -> Secrets and variables -> Actions -> Variables`

新增仓库级 Variable：

```text
MONITOR_URL=http://8.163.27.231
```

这是公开地址，不是 Secret。配置完成后先在 Actions 页面手动运行一次巡检，确认绿色，再依赖定时触发。

## 验收标准

- Actions 页面存在独立的中文生产站点巡检工作流；
- 可以手动运行并成功检查当前生产地址；
- 工作流按 30 分钟计划触发；
- 首页或任一直接引用的 JS/CSS 不可用时，工作流明确失败；
- 临时网络错误会有界重试，不会无限等待；
- 巡检不使用 SSH、不读取部署 Secrets、不修改服务器；
- 原有 `v*` Tag 部署工作流及测试保持通过。

## 不在本次范围内

- 邮件、钉钉或飞书通知；
- Lighthouse 性能、SEO、最佳实践或可访问性评分；
- 自动回退、自动重启 Nginx 或服务器自愈；
- 域名、DNS、HTTPS 和证书监控；
- 深层页面操作、音视频播放或浏览器端交互测试；
- 外部监控平台或自托管 Runner。
