# 移动端相册悬浮操作与原地刷新设计

## 背景

移动端相册页面向上滚动后，顶部品牌区和相册操作区会离开视口，用户无法快速上传照片或刷新列表。当前刷新流程还会把照片网格替换为完整加载状态，在移动浏览器中可能造成文档高度变化和滚动位置跳动。

## 目标

- 在移动端原操作区离开视口后，显示右上角 A3 悬浮胶囊。
- 悬浮胶囊只提供“上传照片”和“刷新”两个操作，不重复占用品牌区空间。
- 刷新保持当前滚动位置和用户正在浏览的照片上下文。
- 刷新期间保持照片网格的布局高度稳定，避免 iPhone Chrome 滚动条跳动。
- 桌面端布局和现有上传、编辑、草稿、登录过期行为不变。

## 非目标

- 不修改照片 API、上传并发策略或照片排序规则。
- 不把操作区永久固定在移动端底部。
- 不在本次改动中引入新的动画库。

## 交互设计

### 初始状态

移动端初始状态继续显示完整的相册标题、照片数量和原有“上传照片”“刷新”按钮。现有文档流布局不变。

### 滚动状态

当原操作区离开视口后，移动端显示右上角悬浮胶囊：

- 上传按钮保留上传图标和“上传”文字。
- 刷新按钮使用刷新图标，并提供可访问名称和悬浮提示。
- 胶囊使用不透明背景、当前莓红色主按钮和安全区顶部间距。
- 胶囊不参与桌面端布局；隐藏时从键盘焦点顺序和辅助技术树中移除。
- 用户向下滚动、原操作区重新进入视口后，悬浮胶囊隐藏。

### 原地刷新

- 点击任一刷新入口都调用同一个刷新动作。
- 刷新开始后不清空已显示的照片网格，不用全屏加载骨架替换内容。
- 刷新按钮进入忙碌状态并阻止重复触发，照片卡片和草稿继续可见。
- 刷新成功后就地合并最新照片数据，保留当前滚动位置。
- 如果当前锚定照片仍存在，优先保持该照片在原来的视觉上下文；照片新增或排序变化不主动把用户带回顶部。
- 如果锚定照片已经被删除，滚动位置保持在可用范围内，并落在相邻内容，不强制跳到顶部。
- 刷新失败保留已有照片和滚动位置，只在现有错误提示区域显示净化后的错误信息。

## 技术设计

- 在 `PhotoLibrary` 内用操作区哨兵和 `IntersectionObserver` 跟踪原操作区是否离开视口；不依赖滚动事件高频计算。
- 悬浮胶囊与原操作区共享上传、刷新处理函数，避免两套业务逻辑。
- 悬浮胶囊使用 `position: fixed`，顶部采用 `calc(12px + env(safe-area-inset-top, 0px))`，右侧使用移动端页面内边距。
- 刷新状态单独建模，不把照片库的 `loading` 状态用于卸载照片网格；初次加载仍可使用完整加载状态。
- 刷新前记录滚动容器的滚动位置和当前可见照片 ID。数据合并后只在浏览器因内容变化产生明显偏移时进行最小的锚定恢复，不调用全局 `window.scrollTo(0, 0)`。
- 不改变现有 `usePhotoLibrary` 的 generation、防旧响应覆盖、草稿和上传缓存保护逻辑。

## 可访问性

- 悬浮刷新按钮有 `aria-label="刷新照片"`，上传按钮保留可见文字。
- 悬浮胶囊隐藏时使用 `aria-hidden` 并从 tab 顺序移除，避免和原操作区产生重复控件。
- 刷新忙碌状态通过 `aria-busy` 或等价状态暴露，但不把焦点移到页面顶部。
- 键盘和触摸操作都调用相同的上传/刷新动作。

## 验证

- 单元测试：原操作区离开视口时显示胶囊，重新进入视口时隐藏；两个入口调用同一动作。
- 单元测试：刷新期间照片网格仍存在，重复点击被阻止，成功和失败都保留刷新前上下文。
- 单元测试：有旧请求竞态时不允许旧响应覆盖新数据或清空照片。
- CSS 合同测试：仅移动端启用固定胶囊，包含 safe-area，桌面端无固定操作栏。
- 运行管理端相关测试、全量测试、typecheck、lint 和前端生产构建。
- 在 iPhone 14 Chrome 复测：页面顶部、照片中段和照片底部滚动三处，确认悬浮胶囊无空隙、无横向溢出，刷新后不回顶。

## 验收标准

1. iPhone 14 Chrome 向上滚动后，上传和刷新操作仍可在右上角使用。
2. 悬浮胶囊不遮挡主要照片内容，不出现顶部空白或安全区穿透。
3. 点击刷新不会把页面滚动位置重置到顶部，也不会清除草稿或已显示照片。
4. 刷新失败时用户仍能看到原照片，并能在当前位置重试。
5. 桌面端、照片编辑器、上传队列和登录过期流程无回归。
